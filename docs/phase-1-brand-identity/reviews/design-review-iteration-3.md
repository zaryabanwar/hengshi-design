## Findings

### BID-DR-I3-001 — MEDIUM — Normative principles still present the founder-rejected Signal Ledger logo as recommended

**Requirement references:** D-006; D-026; D-027; CR-001 sections 1, 3.1, 4, 8,
and 9; BR-006; R-021.

**Exact location:**

- `01-identity-principles.md:21-23` says “The diagonal signal path in the
  recommended mark” represents progression between two boundaries.
- `01-identity-principles.md:64-65` says “The recommended mark” is made from two
  rails, a joining field, and one advancing signal.

**Reproduction:** Compare those current-tense statements with D-027/CR-001 and
`geometry-spec.json:11-15,18-34`. Framework Relay has four open brackets, a
non-diagonal stepped relay, and a square checkpoint; the diagonal two-rail/
joining-field construction is the archived, founder-rejected iteration-2 logo.
A current-package search finds these stale recommended-mark statements only in
`01-identity-principles.md`; the rest of the current authority prohibits a return
to that geometry.

**Impact:** This file is a normative identity artifact and is referenced by the
D-026 traceability row. A designer, motion author, design-system producer, or
reviewer following it would rebuild or animate the rejected mark while other
authorities require Framework Relay. The founder would be asked to approve a
package with two incompatible definitions of the recommended logo.

**Acceptance condition:** Reconcile both passages to the exact current mark:
four open governed brackets, a non-diagonal stepped evidence relay, and square
checkpoint, while preserving the broader Signal Ledger relationship/progression
principle. Then scan every non-archive producer artifact and require any diagonal
two-rail/bridge description to be explicitly labelled superseded or a retained
layout motif, never the current/recommended mark. Add deterministic validation
for the current normative description.

### BID-DR-I3-002 — MEDIUM — Current hybrid application renders a detached checkpoint instead of the authoritative scaled master

**Requirement references:** D-027; CR-001 sections 3.1, 5, 8, and 9; BR-006;
`geometry-spec.json`; `03-logo-system.md:14-44`; R-021.

**Exact location:** `assets/current-hybrid-framework-relay.svg:7-11`, used twice
on the founder board at `visual-boards/index.html:47,113`.

**Reproduction:** The frame and relay use
`transform="translate(88 54) scale(.62)"`. The authoritative checkpoint is local
x=61, y=25, width=6, height=6. Under that transform it must render at
x=`88 + .62*61 = 125.82`, y=`54 + .62*25 = 69.50`, size `3.72`. The source instead
places the checkpoint at x=140.7, y=84.4, offset **14.88 px right and 14.90 px
down**. Those coordinates result from incorrectly scaling the lockup-global
checkpoint position 85/49 rather than the master-local 61/25.

**Impact:** The sole current equal-format application and its large representative
specimen show a detached square between the mark and wordmark, not the exact
Framework Relay logo the founder is being asked to assess. It weakens the claimed
shared spacing/topology and makes the board inconsistent with the otherwise-correct
primary/light/mono/reverse family.

**Acceptance condition:** Place the checkpoint inside the same transformed master
group at local x=61/y=25/6x6, or use the exact computed rendered coordinates
125.82/69.50/3.72. Re-render every board mode and verify the application mark
against `framework-relay-master-80-v1` with a deterministic coordinate check that
covers embedded current-application marks, not only standalone logo files.

### BID-DR-I3-003 — MEDIUM — Current hybrid application uses “Verified” without the exact redundant state grammar

**Requirement references:** D-007; D-026; D-027; BR-008; CR-001 evidence-grammar
retention; `04-color-and-typography.md:67-79`; `BRAND_IDENTITY.md:105-124`.

**Exact location:** `assets/current-hybrid-framework-relay.svg:18-22`, presented
on the board at `visual-boards/index.html:47,113`.

**Reproduction:** The current application displays lime text `VERIFIED INPUT` and
`SOURCE + DATE REQUIRED`, but it provides neither the required filled-circle
marker nor a solid status rail. The nearby cyan stepped path and square are the
logo/layout relay and checkpoint, not the Verified state; current guidance
explicitly prohibits interpreting the checkpoint as an evidence-status marker.
The normative grammar requires Verified = filled circle + solid rail + visible
label/source/date context.

**Impact:** The dedicated state specimen is correct, but the most prominent
current hybrid application breaks the retained system in actual use and relies on
lime plus text. Downstream teams could copy the current application instead of
the table, creating exactly the cross-surface state drift the identity is meant
to prevent.

**Acceptance condition:** If this is a Verified status, add the exact filled
circle and solid status rail, keep the visible label/source/date context, and
describe the same encoding semantically. If it is not a status, replace
“VERIFIED” and lime status styling with non-state wording/tokens. Ensure the logo
checkpoint and layout relay cannot be mistaken for the status marker/line. Add
validation that checks every current visual-source use of the six reserved state
labels, not only the dedicated specimen.
