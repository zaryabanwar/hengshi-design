# 03 — Incremental AI Delivery Workflow — v1

Current authority: [D-097](../../DECISIONS.md#d-097--incremental-ai-delivery-progress-based-corrections-and-session-handoffs), approved 2026-10-25.
The founder directs AI delivery. No separate workflow service, company dashboard,
agent fleet or scheduling layer is required.

## Delivery order

1. Apply the accepted brand and settle shared foundations.
2. Complete the semantic 2D website, content administration and publication.
3. Complete 2D AI guidance, human handoff, booking, privacy and recovery journeys.
4. Deliver the full agreed 3D World against the working shared platform.
5. Qualify the integrated platform for launch under separate operational gates.

These are increments of v1. All fourteen definition subjects, four peer streams
and the accepted campus remain required. Define the relevant increment before
building it; unfinished future 3D details do not block unrelated 2D delivery.

## One session, one outcome

- The founder uses the discussion chat for decisions and the next work prompt.
  Each work chat completes one bounded assignment, reports and stops.
- Read AGENTS.md, the constitution, TASKS.md and PROJECT_STATE.yaml. Inspect Git
  and relevant runtime; find only the owning requirements/decisions/contracts.
  Do not bulk-read historical packets or trust old summaries as current evidence.
- Reuse accepted work. A feature needs relevant spec, plan, tasks and contracts
  before code; reversible in-scope details are engineering work.
- UI needs an approved Figma/Stitch reference for the affected surface. Present
  concrete output for visual acceptance; do not ask to approve unseen work.
- Continue related fixes inside the assignment without repeated permission.
  Do not start another feature, chat, agent fan-out or active-goal operation.

## Engineering and review

Prefer framework built-ins; research version-sensitive behavior using Context7
and official sources. Cite the cause, make the smallest safe fix and exercise the
actual behavior with focused tests. Run affected checks, then the full suite once
per coherent batch when practical. Verify changed UI in Playwright.

Independent review applies to coherent material design batches, requested review,
and money/security/external-system changes. No automatic reviewer for each
document, link, screenshot or fix. Reuse valid evidence and review the delta.
No hard two/three-cycle cap: correct safe in-scope defects while progressing.
If failures repeat, change diagnosis/approach; escalate a real missing decision
or input rather than requesting another iteration. Never waive failing criteria.

## Gates that remain

| Gate | Required before the affected action |
|---|---|
| Material choice | Founder decision for scope, architecture, risk, cost, public claims or authority changes. |
| Design | Relevant approved reference, with independent material design review. |
| Compatibility | Latest mutually compatible stable complete coupled graph for the increment; evidence, reproducible locks and rollback. Include transitive/shared dependencies; qualify unused future graphs later. |
| External/Git | Explicit applicable approval for branches, commits, pushes, migrations, destructive actions, external writes, credentials/providers, spend, publication and deployment. Existing approvals remain valid within scope. |
| Launch | Real accounts/content, legal and operational sign-off, device/load/accessibility qualification, staging, recovery and deployment evidence. |

D-068 defers hosting/provider/region/cost selection. D-095 governs Figma routing
inside approved scope. Consumed method/correction counters do not override D-097;
action boundaries, immutable evidence and safety controls remain.

## Completion and handoff

Use TODO/DOING/DONE/BLOCKED. DONE requires relevant tests and an approved commit;
when commits are deferred, state what passed and that gate without claiming DONE.
Launch readiness is separate. Builds and artifact checks do not prove behavior,
legal compliance or release readiness.

Keep TASKS.md and PROJECT_STATE.yaml within 50 lines. Update the controlling
product reference, at most two documents per slice. No routine narrative reports,
snapshot chains or review packets. Record actual founder decisions once; link
them from other entry points. Preserve existing frozen evidence.

Return the delivered outcome, affected files, tests and visible evidence, genuine
remaining gates, and one recommended next task. Stop for the discussion chat.
