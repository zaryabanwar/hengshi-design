Booking email: prove mailbox access before choosing a slot

Engineering proposal · review in progress This explains the intended booking flow. It sends no email, verifies no code and shows no working booking controls. Visitors need no account or Microsoft sign-in.

  1. Submit the existing briefProvide the six qualification fields and separate booking consent. A valid email spelling alone does not prove access to the mailbox.
  2. Request a confirmation codeThe proposed service sends one eight-digit code to that current address. A queued email, provider acknowledgement or delivery timeout cannot show verified.
  3. Copy, paste, then VerifyUse one labeled field that accepts the whole code, including leading zeroes, and supports browser filling. Opening the email cannot verify anything; the original authorized booking process must submit it.
  4. Continue to eligible slotsOnly a successful current code opens the separately checked availability step. Selecting a slot still needs review and guarded submission; an appointment remains pending until calendar and local evidence agree.

More time without more email

The proposal gives a code ten minutes, warns before expiry and offers explicit More time. Up to ten ten-minute extensions keep the same code and attempt limit; expiry, address change or withdrawal cannot be reversed by an old control.

Correct the address safely

Changing the address invalidates its old code and slot eligibility. A late email can still arrive, but its code cannot verify the corrected address. It never changes a confirmed appointment.

Resend deliberately

A new code replaces the previous one under shared limits. If earlier delivery is uncertain, check that same action before retrying. A new tab or repeated click cannot bypass uncertainty or produce unlimited messages.

Recover a lost response

If Verify succeeded but the reply was lost, check the same action rather than consuming another guess. Its historical result does not mean email verification is still current; the proposed slot-access freshness is thirty minutes.

Mailbox confirmation belongs to this booking. It is separate from staff Microsoft sign-in, conversation access, consent and appointment confirmation. An email code alone cannot recover a lost private process or inspect another visitor’s records.

The method, ten-minute code window, ten extensions, thirty-minute booking-action freshness and abuse limits are proposed design choices. D-076’s conversation inactivity rule remains separate. This panel does not prove accessible interaction, delivery, concurrency or security. Account/adapter capability, exact wire and authorized review projection, policy bindings, secret management, production screens and integrated acceptance remain required.
