# Anonymous private-process access — v1 proposal

Status: DOING. Proposed 2026-10-05. No application, route, account, grant,
persistence, dependency or deployment change. Independent review and integrated
founder acceptance remain required.

## Scope and recommendation

The [interface catalogue](INTERFACE_CATALOG.md#common-boundaries) and its
`process_ownership`/`process_authorization` field rows require process-scoped
visitor proof but leave its transport and lifecycle undefined. This proposal
refines that boundary for IF-CHAT-01–04, IF-BOOK-01–09 and IF-PRIVACY-01/02 under
[security feature 001](../../../specs/001-platform-security-hardening/spec.md),
[data constraints](DATA_CONTRACT.md#conversations-consent-and-handoff) and the
[governed handoff lifecycle](HANDOFF_LIFECYCLE.md). It adds no visitor account,
password, general identity directory or staff role. Staff JWT/bcrypt, Entra and
emergency-access requirements remain unchanged.

Recommend a **server-issued opaque proof for each private process**, delivered
only through an HTTPS HttpOnly cookie. The server binds its verifier to one
process family, selector, proof generation, permitted purposes/actions and
server-controlled validity. Possession proves access to that bounded process,
not a named person's identity, email ownership, consent or business completion.
Selectors and operation IDs remain public-to-the-caller references, not secrets
or alternate credentials. No cookie is minted merely by browsing public pages.

| Proof scope | What it can support after current checks | What it cannot establish |
|---|---|---|
| Chat session | That session's permitted chat/consent/handoff actions and events | Another session, durable storage without consent, staff assignment, live acceptance or media permission |
| Booking lineage | That lineage's qualification and permitted status/actions | Verified email, eligible slot, provider confirmation or another lineage |
| Privacy request | That verified request's minimal safe status | Authority over every record with the same email, deletion of unmapped classes or verified provider/backup removal |

Handoff remains a child of the authorized chat context, not a new transferable
visitor identity. Creating a booking from chat requires an explicit user action
and separately permitted field transfer; it does not clone the chat proof or
join histories by email. A privacy status proof is separately issued only after
the request's target scope has been verified under its approved identity policy.

## Proof and cookie representation

The proposed bearer secret contains 256 independently random bits generated by
a standard CSPRNG; use a canonical base64url representation without padding.
This proposed security margin is not a standards-mandated service limit. Generate
it independently of the process selector and operation ID; do not derive it from
email, timestamps, client input, a device fingerprint or a public digest. Store
only a nonrecoverable verifier under the separately approved cryptographic and
data-storage profile; use constant-time verification. No raw secret belongs in
database rows, replicas, jobs, evidence or telemetry. In the browser, the sole
bearer transport is the protected HttpOnly cookie specified below; do not store
the secret in script-readable storage such as localStorage/sessionStorage or
any other unapproved browser store.

Recommend `Secure`, `HttpOnly`, explicit `SameSite=Lax`, no `Domain`, `Path=/`
and an approved `__Host-` cookie name namespace. Lax supports external safe-page
navigation without permitting a state-changing GET. Prefix enforcement does not
replace attribute configuration, CSRF or object authorization. Cookies are not
isolated by port or browser tab; every application on the credential host is
inside the host trust boundary. Exact host/ingress/proxy choices remain deferred,
but untrusted applications must not share that credential boundary.

Use distinct server-controlled cookie slots for different processes and proof
generations so a late response cannot overwrite a newer credential in the same
slot. The server accepts only the current permitted generation for the selected
process; finding some other valid cookie in the request cannot authorize it.
Reject ambiguous duplicate credential names or malformed/unknown proof variants
before selecting authority; do not depend on a last-value-wins cookie parser.
Exact name syntax, encoding bounds, concurrent-process/cookie/header capacity
and safe cleanup are required transport-profile inputs before wire freeze.

Do not copy a bearer proof into JSON, a query/fragment, a WebSocket subprotocol,
localStorage/sessionStorage, a public page data block, clipboard link or an email.
Only the relevant server boundary may issue `Set-Cookie`. Private responses use
`Cache-Control: no-store`; public HTML/cache derivatives contain no per-visitor
proof, CSRF value or process data. HttpOnly prevents script reads of the cookie;
same-origin malicious scripts can still initiate actions, so it is not XSS safety.
No production attribute is relaxed to accommodate the native prototype.

## Bootstrap and uncertain creation

Recommend two closed phases at the **existing** IF-CHAT-01 or IF-BOOK-01 POST,
without a new endpoint or visible user account:

1. After an explicit Start Chat/Book action, a same-origin bootstrap request can
   allocate only a bounded ephemeral provisional context and issue its proof.
   Its response includes the nonsecret selected context and a separate CSRF
   request token, never the bearer secret. No message, email, qualification,
   consented history or external effect is admitted at this phase.
2. The actual create command supplies its scoped operation identity and CSRF
   request proof, and presents the provisional cookie. The server checks current
   provisional authority, exact closed input and permitted purpose before
   promoting that context to its single process and recording any allowed result.
   Promotion and its operation outcome use the governing process's atomic or
   reconciled authority; retries never dispatch the create again merely because
   an acknowledgement was lost. No durable personal data precedes its legal gate.

Initial bootstrap relies on exact trusted-source Origin checks and the approved
browser request/media profile because no synchronizer secret exists yet. Missing,
null, malformed or unapproved Origin denies this browser-only POST; it is not a
public safe GET, permissive form route or nonbrowser service credential. Its
allocation still needs finite abuse/work bounds. A lost bootstrap response may
leave an empty provisional context that expires under the approved policy; no
claim of exactly-once allocation follows. Cookie slots and initiating UI
generation distinguish a late bootstrap response from the chosen context.

Once the proof is issued, the selected provisional context scopes the create
operation. Changed input under the same operation conflicts. Uncertain promotion
reconciles that operation under current proof and disclosure authority, rather
than creating a new process to evade uncertainty. A context/proof alone never
proves that promotion or an external action completed. Exact bootstrap/create
envelopes, state variants, admission constraints and expiry are still required.

IF-PRIVACY-01 has different authority: verify the requested target scope using
the approved existing-process or independently reviewed subject-verification
procedure before admitting its deletion intent or issuing a request-status
proof. Knowing an email, selector or operation reference is insufficient. A
status cookie does not retrospectively verify identity or broaden deletion.
Missing identity/recovery policy leaves that affected operation unavailable.

## HTTP and WebSocket request protection

Recommend a server-generated synchronizer CSRF token bound to the selected
process and current proof generation. It is distinct from the HttpOnly bearer
secret, cannot grant access alone, and is delivered only by a permitted private
response. For protected HTTP mutations use the approved custom-header transport,
exact origin check and current cookie proof together. Do not accept query-token,
arbitrary form or content-type fallbacks. Public GETs require none of this;
private safe reads still require their own current process/disclosure authority.
No wildcard CORS, sibling-domain suffix match or `Origin: null` is trusted.
Target-origin/proxy trust and every direct ingress path need explicit validation.

Refresh/bootstrap information must be obtained through the existing authorized
process boundary, never an unprotected global token endpoint. Missing Origin
handling for an authorized safe read must use the reviewed request profile;
HTTP/browser contexts do not all supply identical headers. Neither SameSite,
CORS, Origin nor the CSRF token alone proves process ownership. Unknown binding
or authority denies before effects and private status/existence disclosure.

For IF-CHAT-03, verify the exact allowed browser Origin, current chat cookie,
selected session, validity and eligible context **before accepting** the
WebSocket. Browser WebSocket APIs do not offer arbitrary application headers;
the HTTP custom-header convention cannot simply be reused. Recommend a closed
first initialization frame containing the separate process-bound CSRF request
token. No private event, history, subscription or business command is delivered
or processed before that check. Initialization has a finite approved deadline,
frame/connection/work bounds and safe rejection; credentials are never echoed.

An initialized socket still requires current proof generation, consent/purpose,
process state, source eligibility and current assignment at every relevant
message, replay and outbound delivery decision. Lost authorization stops
disallowed queued delivery and closes the channel; startup checks and a periodic
timer cannot prove immediate revocation. The handoff contract's delivery/fencing
obligations govern in-flight work. IF-STAFF-15 uses separate staff identity and
assignment, never the visitor proof. Protocol/ack/replay formats and numerical
limits remain in their directional event contracts; no tutorial echo behavior,
URL token or unbounded in-memory connection manager is adopted.

## Revocation, storage and recovery

Proof validity, consent expiry, staff availability, booking challenge validity
and record retention are separate clocks. No staff 30-minute/eight-hour session
policy or visitor 90-day record rule automatically sets this proof's lifetime.
Expiry, revocation and proof-generation changes are enforced by current server
authority, not browser cookie expiry, closing a tab or deleting a local cookie.
Restored browser sessions or backups cannot resurrect a revoked proof or renew
retention. A proof missing from its authoritative store is not reconstructed from
another process, an email, cached metadata or a remembered signed cookie.

Keep non-consented chat, replay and its proof/CSRF metadata in the bounded
ephemeral path; no snapshots, persistence, logs or queue payload may silently
make that path durable. A consented process's durable records and any durable
proof/verifier require their own class-specific purpose, duration, deletion and
restore mapping. Hashes and identifiers remain linkable private metadata.
Unknown classifications or legal/store policy deny the affected persistence.
This proposal chooses no SQL columns, Redis persistence setting or retention
period and creates no visitor identity history.

Rotate/revoke proof generations when an approved authority transition requires
it, with old generations unable to authorize new data/actions or replay after
the fence. A cookie rotation response lost in transit can cause loss of access;
an unverified fallback or unlimited old-token overlap is not recovery. The
physical plan must handle issuance/promotion/rotation interleavings, lost replies,
cookie eviction and bounded cleanup. Unknown business outcomes remain intact;
loss of access cannot report cancellation, deletion, termination or confirmation.
Cross-device/email-link recovery needs a separately reviewed identity/proof
flow. No recovery secret in a URL or automatic new booking dispatch is implied.

Ending/deleting chat may invalidate its chat proof while a separately authorized
privacy request retains only its own permitted outcome projection. That status
proof does not recover deleted conversation content, extend its retention or
certify unmapped provider/backup deletion. Alias ownership remains undecided.
Proof loss explains access unavailable and keeps semantic content/Contact/Book
reachable; it does not claim a working recovery channel, owner or response SLA.

## Required implementation evidence and remaining decisions

After the applicable approvals, exercise actual HTTP, browser, store and socket
boundaries with synthetic data: wrong family/object/generation; guessed selectors;
cookie duplication/fixation; hostile/missing/null Origin; absent/mismatched CSRF;
query/body credential rejection; unknown/stale bootstrap and lost promotion;
multiple tabs and late Set-Cookie; no private disclosure before WS initialization;
revocation versus queued delivery; email correction/verification not granting
another lineage; lost/expired proof; cookie eviction; consent refusal and store
loss; deletion versus minimal status; and restore predating revocation. Check
permitted controls as well as denials. Definition examples are not runtime tests.

Before wire freeze approve the two-phase envelopes, per-family purpose/action
and identity-recovery policy, name/secret/CSRF transport profiles, cookie support
and measured capacities, exact expiry/renewal/rotation and finite work limits,
current-authorization/atomic admission and revocation fences, cryptographic
verifier handling, legal class/store/backup mappings and compatible stable graph.
Production UI references and founder acceptance remain separate. No deployment
provider, host, staff grant, legal basis or public operating claim is selected.

## Dated primary and framework observations

Checked 2026-10-05. Sources support the limited mechanics below, not acceptance
of Hengshi's two-phase/per-process design or automatic framework enforcement.

- [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
  recommends random server-issued secrets, one-way verifier storage and server
  expiration. Session-cookie restoration and cookie deletion do not prove
  revocation. The 256-bit margin and process binding above are this proposal.
- [Mozilla Set-Cookie reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)
  describes Secure/HttpOnly/SameSite, host-prefix restrictions and browser cookie
  behavior; these attributes provide no object-level access decision.
- [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
  supports synchronizer tokens for stateful applications, robust source/target
  origin validation and framework protections before custom machinery.
- [OWASP WebSocket guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
  supports pre-upgrade origin checks, current session/message authorization and
  finite resource protection. Its example timer/size numbers are not adopted.
- Context7 `/websites/fastapi_tiangolo` and official [cookies](https://fastapi.tiangolo.com/advanced/response-cookies/)
  and [WebSockets](https://fastapi.tiangolo.com/advanced/websockets/) confirm
  framework cookie emission and dependency injection, not full CSRF/revocation
  enforcement. Reuse those primitives; do not copy the tutorial's query-token
  and credential-echo examples or replace accepted process authority with them.
- Official [Starlette session documentation](https://starlette.dev/middleware/)
  describes readable signed-cookie session data. It does not supply the proposed
  opaque server-state proof. The [native source observations](../../../output/research/private-process-proof-2026-10-05/native-framework-observations.json)
  identify observed prototype versions and source lines: `set_cookie` requires
  explicit Secure/HttpOnly arguments; signed session data uses base64 JSON, and
  that optional middleware cannot import here because `itsdangerous` is absent.
  No installation was attempted; neither observation selects a production version,
  CSRF middleware or complete stable graph.
